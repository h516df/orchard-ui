# 云端项目工作流 0.2

## 起点

本目录为跨项目通用入口。[CORE.md](https://github.com/h516df/vibe-ui-quality-kit/blob/main/workflow/CORE.md) 的同版简约规则保存到每个项目默认分支的 AGENTS；不以跨私有仓库读取成功作为开始工作的前提。代理按任务核对相关 PR 和对应分支交接，新项目建仓时接入；详见 [采用状态](https://github.com/h516df/vibe-ui-quality-kit/blob/main/workflow/REPOSITORIES.md)。

用户已明确要求：这套流程默认由代理处理，不要求用户逐项目提醒、复制启动语或执行接入命令。规则已知且目标项目获授权时，自动采用适用步骤；沿用已有接入，必要澄清集中处理。跨会话自动生效以实际加载的项目/全局指令为准，不能把私有 GitHub 存档称为账户级配置。

先读项目 AGENTS、README、CLOUD_DEVELOPMENT、HANDOFF 和任务相关规则。核对远端默认分支、进行中分支、PR 与未提交改动，接续已有成果。用户当前指令优先；不得因通用模板增加与任务无关的审批或覆盖项目约定。全程使用已授权云端环境。

## 1．区分讨论、收集与实施

代理根据自然语言和当前阶段判断，不要求固定口令，也不把每个新任务强制放进等待队列。

- 用户明确要求开发新项目、修改、修复或继续实施：整理简短范围后直接执行，不再询问是否开工。
- 用户说先讨论、先记下、候选想法，或在反馈阶段零散指出体验问题：更新项目需求池；不改产品、不触发构建、不重新发布。存在歧义时先记录可确认部分，只集中澄清会改变主要含义的内容。
- 对当前任务计算口径、数据含义或本批错误的纠正及时纳入。独立新增功能默认进入下一批候选；不把澄清和缺陷一律推迟。当前用户的暂停、收集或立即处理指令优先。

由代理保留用户原话、场景、期望效果和状态，自己的推测单列；候选不是实现承诺。只保留一份需求状态，PR、TASK 和 HANDOFF 用链接引用。细则见 [需求与批次](https://github.com/h516df/vibe-ui-quality-kit/blob/main/workflow/INTAKE.md)。

每批围绕一个相关体验或明确结果，代理写明例子、2–5 条完成条件、当前边界和重要依赖。按价值与风险建议顺序，避免把全部积压变成大版本；用户无需打分、填表或管理排期。批内分步实现并检查，集中交付一个完成预览；不要把“一次交付”误解为只能一个提交、一个 PR 或等全部项目功能完成。

新项目先查当前环境与账号能力，路线见 [云端能力与建仓](https://github.com/h516df/vibe-ui-quality-kit/blob/main/workflow/CLOUD_CAPABILITIES.md)。不能在收到明确实施请求后，只记一条待办便结束。

## 2．先复用，再实现

优先检查现有项目/组件；有明确不确定点再查官方文档或 GitHub，并记录来源、许可证、适用范围和采用结论。已有证据足够时不重复联网。用户体验保持少步骤，常用路径少必填项，次要信息按需展开。

视觉任务先确定字体、字阶、间距、材质、圆角、图标、菜单、导航、动效、暗色/减少动态效果。已有设计系统则复用。不要求用户逐组件审批；显著改变方向时先展示代表页面。外观检查包括空状态、错误、加载、长文字和小屏，不能只看默认静态画面。动效在实际运行中核对，必要时提供短录屏；检查快速连续操作、中途切换和减少动态效果。截图通过不能证明动画自然。

## 3．一份主要源码，小步实现

以指定 GitHub 仓库及任务分支为长期源码依据。一个任务或相关批次沿用一个分支；独立任务隔离。复杂批次可关联多个小 PR，不因此增加用户查看版本的次数。变更同时更新必要说明，不重写无关历史。

优先修改已有实现，避免通过 v3/v4/v5 不断覆盖同名逻辑。发现结构债务时只整理当前任务需要的范围，先保证数据兼容，不顺带重写整个项目。

预览、检查和发布应追溯到相同源码内容。平台必须使用第二个托管源码库时，记录来源 SHA、平台 SHA、产物校验/比对和部署 ID，不能把两个仓库的 SHA 写成相同。传输失败先检查参数、大小和响应格式，不盲目重复整份上传。

## 4．按风险检查，保留证据

- quick：语法、配置、必要的静态检查；文案/颜色等轻改通常只需相关检查和目标画面。
- core：涉及金额、状态保存、导入、迁移、权限或主要交互时，运行相应计算与浏览器用例。稳定环境执行关键页面截图比较；截图不能判断审美是否合意。
- 扩展：只有跨模块变更、失败或剩余风险才扩大范围。一次相关检查通过后停止重复运行；新改动仅复查影响范围。失败先定位，再重跑相关项。

计算测试覆盖用户例子和有意义的边界；浏览器用例尽量通过可见文字/角色操作，数据相互隔离，使用自动等待而不是固定睡眠。依赖锁定、日期固定、截图同环境。失败时记录截图/trace；不要默认保存真实账单或凭据。

每项标注 passed / failed / not run、执行命令、日期、来源提交。干净提交上运行的结果绑定该提交；若在工作树验证，注明基线+文件状态，提交后核对内容。旧会话通过不等于当前通过。未配置的检查、守卫脚本、演示数据、模拟器和真机的能力要分别说明。

## 5．自动化稳定动作，按授权发布

文档整理可按风险省略无关业务构建；使用 skip-ci 标记前核对保护要求，不能跳过分支保护要求的检查或伪造成功状态。若必须检查，使用现有流水线验证原提交，合并相同源码时避免重复触发无关构建。

先跑已确定的廉价检查，再运行必要功能检查；CI 同分支新提交取消过时的检查任务。限制超时、依赖安装次数及失败附件保留期。不默认引入多代理、定时任务、收费后端或新平台。

修改 GitHub Actions 时使用固定版本的工作流语义校验（例如 actionlint），检查表达式上下文和字段；单纯 YAML 解析不能替代。

源码先提交并推送，再从该提交打包。使用现有发布工具和访问范围；已有授权内推进，保留私有权限。没有授权的公开发布、不可逆动作或对外发送另行处理。发布工具成功后记录 URL、源码提交和部署标识；检查非终态直到明确结果。不能把已保存版本称为已上线。

通用检查工具不负责管理平台密钥或直接部署；各项目通过原有官方接口适配。不要把敏感输出写入交接或附件。PR 自动检查不授予默认写权限，不用 pull_request_target 执行不可信代码。

## 6．交付与接续

需求池分别记录候选、待做、开发中、已验证和已发布，阻塞与证据另列。检查通过、源码保存、部署成功和实体设备验收不能混为“完成”。只更新本批条目；长期需求池保持打开，不用关闭关键词把整池自动关闭。

发布前保留上版来源提交、产物/部署标识及恢复说明。涉及持久化格式变化先明确备份、迁移和恢复路径并验证；保留旧 APK 不代表 Android 支持直接降级。安卓项目按需采用 [交付验收模板](https://github.com/h516df/vibe-ui-quality-kit/blob/main/workflow/templates/ANDROID_DELIVERY.md)，不把模板当作已接通。


更新现有 HANDOFF 顶部简短当前摘要，历史保留在下方或独立归档并链接，不每次复制整份聊天。长期偏好写 AGENTS；当前任务进度留任务/交接文档，避免不断复制一整套说明。模板变更记录版本与目标项目采用的提交。

把源码、检查配置和交接一起提交推送，核对远端分支 SHA。新任务建立 PR，延续任务更新原 PR；不擅自合并其他任务。CI 实际完成前标 pending/not run，失败说明具体原因。最终给可用结果、主要变化、检查范围和仓库/分支/PR/准确提交；附一句接续提示。

用户集中判断“是否符合生活方式、是否舒服”，代理承担功能核对、错误定位、备份和发布工作；必须人工完成的设备授权或真机反馈，说明原因并压缩到必要步骤。
